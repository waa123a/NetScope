# AI 开发流程手册

> 以 NetScope（本地 IP / 端口扫描器）为实例，整理一套不依赖特定 AI 模型的开发流程。
>
> 目标：换模型后，仍能按同样的节奏、同样的验收标准，做出同样完整度的软件。

这套流程面向“一个人 + AI”开发本地工具、桌面应用和小型 Web 应用。它不假设模型一次做对，而是让错误尽早暴露、每次修改都可回归、换模型时不丢项目状态。

对于多人协作的大型系统，还需要在此之上增加 CI、代码评审和分支策略；本文不展开。

---

## 0. 先记住四件事

可复制的不是“神级提示词”，而是四样东西：

1. **可验收的规格**：每条需求都能用观察到的行为判断真假。
2. **稳定的接口契约**：模块、API、数据格式先定，再写实现。
3. **每步可核对的证据**：命令输出、测试结果、HTTP 响应、真实界面。
4. **存在文件里的项目状态**：不依赖聊天记录，换模型只交接文件。

一句话：**流程 > 提示词 > 模型**。

### 模型常见偏差与流程对策

| 常见偏差 | 后果 | 流程对策 |
| --- | --- | --- |
| 没运行就宣称“已完成” | 交付物不可用 | 每条结论必须附命令、响应或测试结果 |
| 一上来大范围重写 | 引入无关回归 | 冻结公共接口，限定改动范围，一次只改一个根因 |
| 只修表象 | 同类问题反复出现 | 先写根因和验证方法，再允许改代码 |
| 上下文丢失 | 重复劳动、前后矛盾 | 四个状态文件 + 阶段门禁，聊天记录不作事实来源 |
| 过度设计、乱加依赖 | 打包困难、维护成本高 | 明确非目标，设置依赖预算，优先标准库 |
| 界面漂亮但不可用 | 用户点不到、流程走不通 | 真实浏览器验收，逐项检查空/加载/错误/成功状态 |
| 只在开发环境正确 | 换机器、换目录就坏 | 空目录冷启动、重启持久化、路径分离测试 |
| 交付时夹带测试数据 | 用户首次打开看到脏数据 | 发布前清理数据目录，列入发布清单 |

## 1. 全流程：8 个阶段与门禁

| 阶段 | 要回答的问题 | 主要产出 | 通过条件（门禁） |
| --- | --- | --- | --- |
| 0 立项 | 做什么、不做什么、怎样算成功 | 一页项目简报 + 验收标准 | 每条验收都能被观察和复现 |
| 1 方案 | 边界在哪、契约是什么 | 架构说明 + API/数据契约 + 测试策略 | 不写实现也能评审清楚 |
| 2 最小闭环 | 最短路径能否跑通 | 可运行的纵向切片 | 一次真实扫描端到端成功 |
| 3 界面 | 用户能否看懂并操作 | 完整页面、状态与交互 | 浏览器实测完成核心任务 |
| 4 功能迭代 | 每个反馈是否真正闭环 | 任务卡 + 修复 + 回归 | 验收语句全部成立，旧功能不回归 |
| 5 加固 | 哪里会坏、如何失败 | 失败场景清单与修复 | 对抗测试通过，错误可解释 |
| 6 打包 | 换台机器能否独立运行 | 单文件 exe + 构建说明 | 空目录冷启动、重启后数据仍在 |
| 7 交付 | 用户能否独立使用 | 成品 + 使用说明 + 已知限制 | 无测试数据，路径与操作清晰 |

**门禁的意思是：不通过就不进入下一阶段。** 小项目可以把阶段合并，但不能跳过验收。

## 2. 阶段 0：把需求变成可验收的句子

大多数返工不是代码问题，而是目标模糊。开工前只写一页，不要写功能清单式的空话。

### 项目简报模板

```markdown
# 项目简报：<名称>

## 一句话目标
<谁，在什么场景下，用它完成什么>

## 必须做（P0）
- ...

## 明确不做（Non-goals）
- ...

## 运行形态与约束
- 开发环境：
- 交付形态：源码 / 安装包 / 便携 exe
- 依赖预算：
- 权限要求：
- 数据位置：
- 网络与隐私边界：

## 验收标准（可观察）
1. ...
2. ...

## 风险与未知
- ...
```

### NetScope 的填写示例

- **目标**：在 Windows 本机扫描局域网 IP 和端口，查看设备类型与 MAC，保存历史，最终以免安装 exe 运行。
- **必须做**：CIDR/单 IP/末段范围输入；TCP 端口扫描；ping + TCP 兜底发现；任务取消；历史记录；CSV 导出；中文界面。
- **明确不做**：公网扫描、漏洞利用、需要管理员权限的功能、云端上传、多用户、遥测。
- **运行形态**：开发用 Python 3.13；交付为单文件 Windows exe，不要求用户安装 Python。
- **验收**：双击 exe 不弹控制台窗口，能打开页面；扫描 `127.0.0.1` 能显示 IP、设备类型、MAC、端口；关闭再打开历史仍在；CSV 可打开；启动无报错弹窗。

### 三条硬规则

1. **验收标准必须是行为，不是形容词。**
   - 差：扫描要快、界面要好看。
   - 好：扫描 1 个地址的 1 个端口，2 秒内返回结果；结果表能显示设备类型和 MAC。
2. **“明确不做”必须写。** 它是防止 AI 扩张范围的刹车。
3. **先定运行形态。** 源码、安装包、便携 exe 会影响架构、路径和依赖选择，不能最后才想。

### 开工提示词

```text
先不要写代码。请基于下面的项目简报：
1. 用 5 行复述你对目标的理解；
2. 列出所有歧义、隐含假设和需要我决定的问题；
3. 给出最多 3 种技术方案及取舍；
4. 给出主要风险清单。
等我确认后再进入方案阶段。

<粘贴项目简报>
```

**门禁**：你能用一句话说清“不做什么”，并能用可观察的行为验收每一条 P0。

## 3. 阶段 1：先定边界和契约，再写代码

### 3.1 模块边界

NetScope 的划分：

```text
ip-scanner/
  app.py          # HTTP 服务、路由、静态资源、CSV
  scanner.py      # 目标/端口解析、探测、任务管理、MAC/设备类型
  oui.py          # 离线 IEEE OUI 厂商前缀表（生成物）
  history.py      # 历史持久化
  static/         # HTML / CSS / JS
  tests/          # 单元与集成测试
  portable/       # 交付物
```

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| `scanner.py` | 解析、探测、任务状态、设备信息 | HTTP、HTML、文件下载 |
| `oui.py` | MAC 前缀到厂商的离线映射 | 设备类型判定（由 scanner 组合特征） |
| `app.py` | 本地服务、鉴权、路由、CSV | 扫描算法细节 |
| `history.py` | 记录读写、上限、原子替换 | 界面展示、扫描逻辑 |
| `static/` | 展示与交互 | 业务规则、权限判断 |

边界清楚的好处是可测试、可替换，也让新模型知道“这个需求应该改哪里”。

### 3.2 契约先写出来

NetScope 的关键 API：

| 方法 | 路径 | 说明 | 鉴权 |
| --- | --- | --- | --- |
| GET | `/api/state` | 当前任务快照 | 否 |
| GET | `/api/network` | 本机地址与 /24 网段 | 否 |
| GET | `/api/history` | 历史摘要列表 | 否 |
| GET | `/api/history/{id}` | 单条历史详情 | 否 |
| GET | `/api/export` | 导出当前结果 CSV | 是 |
| GET | `/api/history/export?id=` | 导出历史 CSV | 是 |
| POST | `/api/scan` | 启动扫描 | 是 |
| POST | `/api/stop` | 停止扫描 | 是 |
| POST | `/api/history/delete` | 删除一条历史 | 是 |
| POST | `/api/history/clear` | 清空历史 | 是 |

同时明确：

- 写请求必须是 `application/json`，请求体上限 16 KB。
- 鉴权使用启动时生成的随机会话令牌，通过 `X-NetScope-Token` 传递。
- 服务只监听 `127.0.0.1`，不对外网开放。
- 并发扫描只允许一个，重复启动返回冲突错误。

### 3.3 数据契约

扫描结果至少包含：

```text
ip, hostname, deviceType, mac,
ports[{port, service}], latency, foundAt
```

历史摘要与历史详情要分开：

- 摘要列表不返回完整 `results`，避免列表接口过大。
- 详情接口才返回 `results`。
- 历史最多保留 50 条。

这类区分如果等到界面做完再补，通常会引起连锁改动。

### 3.4 失败模式清单

在方案阶段就列出“会怎么坏”：

| 场景 | 期望行为 |
| --- | --- |
| 目标格式错误 | 返回可读错误，不启动任务 |
| 端口超出范围 | 返回可读错误 |
| 已有任务运行 | 拒绝新任务并说明原因 |
| 用户中途取消 | 停止排队任务，状态为“已停止” |
| ICMP 被限制 | 用 TCP 探测兜底 |
| 拿不到 MAC | 显示空值，不伪造 |
| 端口被占用 | 启动失败并给出明确提示 |
| 历史文件损坏 | 当作空历史启动，不崩溃 |

### 3.5 测试策略

| 层级 | 工具 | 覆盖 |
| --- | --- | --- |
| 纯函数 | `unittest` | 目标解析、端口解析、MAC 解析、OUI 映射、设备类型（主机名/端口/厂商组合） |
| 集成 | 本地临时 TCP 服务 | 端口探测、任务完成、取消 |
| 持久化 | 临时目录 | 新增、读取、删除、上限、自动归档 |
| 端到端 | 真实启动 + HTTP + 浏览器/桌面窗口 | 启动、扫描、历史、导出、关闭确认、重启 |

### 方案提示词

```text
基于已确认的项目简报，输出架构说明，不要写实现代码：
1. 模块边界与文件树，每个模块负责什么、不负责什么；
2. 对外契约：API 的方法、路径、请求、响应、错误码；
3. 数据模型与持久化格式；
4. 失败模式与降级策略；
5. 测试策略：哪些用单元测试，哪些必须真实运行；
6. 关键决策及替代方案。
标出所有需要我决定的问题。
```

**门禁**：一个没参与的人只看文档，就知道新功能该改哪个文件、接口会不会变。

## 4. 阶段 2：做一个能跑通的最小闭环

不要先做完整 UI，也不要先做所有功能。先让一条真实路径从头到尾跑通。

### 推荐顺序

1. **解析器 + 测试**：目标、端口、边界值。
2. **探测原语**：TCP 连接、ping、超时。
3. **任务管理**：状态、并发、取消、结果收集。
4. **HTTP 服务**：路由、鉴权、错误处理。
5. **最小页面**：能启动、能看状态、能看结果。
6. **端到端验证**：真实扫描一次。

这个顺序的理由：每一层都能在下层稳定后独立测试，UI 最后绑定稳定接口，避免边改接口边改页面。

### NetScope 的 MVP 验收

```bash
python app.py --no-browser --port 8765

curl -s http://127.0.0.1:8765/api/health
# {"ok": true, "name": "NetScope"}
```

页面会注入会话令牌，测试时可以这样取出并启动扫描：

```bash
token=$(curl -s http://127.0.0.1:8765/ \
  | sed -n 's/.*__SCAN_TOKEN__ = "\([^"]*\)".*/\1/p')

curl -s -X POST http://127.0.0.1:8765/api/scan \
  -H "Content-Type: application/json" \
  -H "X-NetScope-Token: $token" \
  --data '{"targets":"127.0.0.1","ports":"8765","scanPorts":true}'
```

然后轮询 `/api/state`，确认状态从 `running` 变为 `completed`，结果里有 IP 和开放端口。设备类型、MAC、历史等留到后续迭代，不要一次塞进 MVP。

### MVP 阶段刻意不做的事

- 不做完整视觉设计。
- 不做历史记录。
- 不做打包。
- 不做批量导入导出。

不是这些不重要，而是它们会掩盖“核心链路是否真的通”这个问题。

### MVP 提示词

```text
目标：实现一个可运行的最小闭环，不追求完整 UI。
范围：<列出 3-5 项>
要求：
1. 先给实现顺序和每步验证方式；
2. 每完成一层就运行对应测试；
3. 最后必须真实启动一次，完成一次端到端操作，并贴出实际输出；
4. 不要添加未批准的依赖。
```

**门禁**：不是“代码写完了”，而是“真实启动、真实扫描、真实看到结果”。

## 5. 阶段 3：界面要覆盖状态，而不只是好看

### 5.1 先信息架构，后视觉

NetScope 的结构：

- 左侧：扫描控制台、扫描历史。
- 主区：目标与端口输入、开始/停止、统计、结果表。
- 历史：记录列表 + 详情弹层。
- 全局：主题切换、连接状态、错误提示。

一个页面只保留一个主行动（开始扫描），危险操作（清空历史）必须二次确认。

### 5.2 状态清单

| 状态 | 界面必须表现 |
| --- | --- |
| 空闲 | 可输入、可开始、结果区为空状态 |
| 运行中 | 进度、已发现数量、可停止、开始按钮禁用 |
| 停止中 | 明确显示正在停止 |
| 已完成 | 结果、统计、导出可用 |
| 已停止 | 保留已发现结果，说明未完成 |
| 出错 | 可读错误 + 重试路径 |
| 无结果 | 解释原因，而不是空白 |
| 历史为空 | 引导去扫描 |
| 历史详情 | 记录元信息 + 设备列表 |

### 5.3 交互检查

- 整行可点击，而不是只有一个小按钮。
- 支持键盘 Enter / Space 打开记录。
- 焦点可见，按钮有 hover / active / disabled 状态。
- 扫描中禁止重复启动；停止操作不丢已有结果。
- 删除、清空有确认。
- 表格在窄屏可横向滚动，不挤压列。
- **页面状态不能只由“我发起的操作”驱动。** 扫描运行中要高频刷新（400 ms），空闲时也要有心跳（2 s），否则别的窗口、别的客户端或重启后的服务改了状态，当前页面永远看不到。NetScope 曾因此出现“接口里已经有 8 台设备，界面还写着 0 台”的错位。

NetScope 的“历史点不开”就是典型的交互问题：数据和 API 都正常，但可点击区域只有一个很小的“查看”按钮。**能用 ≠ 好用。**

### 5.4 视觉检查

- 颜色、字号、间距用统一变量，不散落魔法值。
- 明暗两套主题都要检查对比度。
- 数字、IP、MAC 使用等宽字体，便于扫读。
- 空状态、加载态、错误态与正常态同样认真。
- 不靠颜色单独表达状态，配合文字或图标。

### 5.5 真实验证

不要只检查代码。至少做：

1. 真实运行：浏览器打开页面；如果交付形态是桌面窗口，还要在实际窗口里验收，而不是只看浏览器。
2. 控制台无错误。
3. 完成一次核心任务。
4. 检查空、运行、完成、错误四种状态。
5. 键盘走一遍主要操作。
6. 宽、窄窗口都检查布局；桌面窗口还要在 100% 和 150% DPI 下检查尺寸与滚动。
7. 截图或 DOM 快照留档；截图不可用时，记录关键元素的几何与计算样式。

### 界面提示词

```text
按现有设计语言实现 <页面/组件>。
必须覆盖：空、加载、运行、成功、错误、禁用状态。
交互要求：主操作唯一；整行可点击；键盘可达；危险操作二次确认。
完成后用真实浏览器打开，报告：
- 控制台错误；
- 关键交互的实际结果；
- 窄屏布局；
- 仍存在的视觉或可用性问题。
不要只描述代码，不要用“应该可以”代替验证。
```

**门禁**：第一次使用的人，不需要额外解释就能完成核心任务。

## 6. 阶段 4：功能迭代的六步闭环

这是整个流程最核心的部分。每个需求、每个 bug 都走同一套循环。

### 六步法

1. **复现**：记录精确步骤、期望、实际、环境。
2. **定位**：给出根因假设，并用证据排除其他可能。
3. **定验收**：写一句可判断真假的验收语句。
4. **最小改动**：只改与根因相关的代码，不顺手重构。
5. **双层验证**：自动化测试 + 真实使用路径。
6. **回归**：跑全量测试，并手动检查一个相邻功能。

### 任务卡模板

完整模板见 [project-template/TASK_CARD.md](project-template/TASK_CARD.md)，核心字段：

```text
现象/需求：
期望行为：
复现步骤：
影响范围：
验收语句：
不允许改动：
验证方式：
```

### 根因分类

先把问题归到正确的层，避免“什么都怪缓存”：

| 类型 | 典型表现 | 先查什么 |
| --- | --- | --- |
| 数据问题 | 记录存在但没有设备 | 记录内容、扫描结果、过滤条件 |
| 界面问题 | 数据正常但用户点不到 | 点击区域、事件绑定、层级、禁用状态 |
| 环境问题 | 开发机正常，另一台不对 | 网卡、权限、ARP 缓存、虚拟适配器 |
| 语义问题 | 用户输入被理解成另一个意思 | 解析规则、默认掩码、边界 |
| 打包问题 | 源码正常，exe 404/崩溃 | 资源路径、可写目录、工作目录 |
| 性能问题 | 卡顿、超时、线程耗尽 | 并发上限、超时、锁、轮询频率 |

### NetScope 的真实案例

| 反馈 | 根因 | 修复 | 验证 |
| --- | --- | --- | --- |
| 历史记录点不开 | 数据和 API 正常，只有小按钮可点 | 整行可点击，补键盘操作和“查看详情” | 浏览器点击、键盘打开、0 设备记录也能解释 |
| 本机 MAC 和实际不一致 | `uuid.getnode()` 取到了 VMware 虚拟网卡 | 用活动 IP 匹配 `ipconfig /all` 中对应网卡段 | 单元测试样例 + 实机 MAC 对比 |
| 扫描 `192.168.6.0` 没有设备 | 不带掩码按 `/32` 处理，只扫一个地址 | 明确输入语义，支持 `/24` 和 `1-254` 范围 | 解析测试 + 实际网段扫描 |
| 结果里的“发现耗时”没用 | 产品信息优先级问题 | 换成设备类型和 MAC，CSV 与历史详情同步 | UI、CSV、历史详情三处回归 |
| exe 启动后静态资源 404 | 打包后资源路径重复拼接 | 只读资源用 `_MEIPASS`，可写数据用 exe 同级目录 | 空目录冷启动 + 页面加载 |

### 迭代纪律

- **一次只修一个根因。** 不要在同一轮同时改算法、界面和打包。
- **不接受“可能是缓存”。** 清缓存后仍能复现，才算证据。
- **修复必须带回归。** 至少覆盖原问题 + 一个相邻功能。
- **不要为了通过验收而改验收。** 需求变更要走项目简报的变更记录。


**门禁**：原问题被真实复现并修复，验收语句成立，全量测试通过，相邻功能未回归。

## 7. 阶段 5：主动加固，而不是等用户踩坑

让 AI 扮演攻击者和挑剔用户，把失败场景列出来，再逐项处理。

### 7.1 加固清单

| 类别 | 要问的问题 | NetScope 的做法 |
| --- | --- | --- |
| 输入 | 空值、超长、非法字符、越界数字 | 目标/端口上限 1024；超时 0.2-5 秒；并发 1-256 |
| 网络 | 超时、断网、ICMP 被禁 | 每个探测有超时；邻居缓存判定存活，ICMP 只用于跨网段目标 |
| 并发 | 重复启动、取消、线程泄漏 | 单任务锁；取消事件；线程池有界 |
| HTTP | 未授权写入、超大请求、错误方法 | 本地绑定；令牌鉴权；JSON 限制；16 KB 上限 |
| 浏览器 | XSS、点击劫持、缓存敏感数据 | CSP；`X-Frame-Options: DENY`；`no-store` |
| 持久化 | 并发写、文件损坏、无限增长 | 线程锁；临时文件原子替换；最多 50 条；损坏时按空历史启动 |
| 输出 | Excel 公式注入、编码乱码 | CSV 加 UTF-8 BOM；对可疑主机名加前缀 |
| 隐私 | 外发数据、遥测 | 不访问外网；不上传；不收集 |
| 体验 | 错误不可读、无取消、无空状态 | 中文错误；可停止；空状态引导 |

### 7.2 存活判定：别让 ping 决定一切

“哪些设备在线”是扫描器的核心结论，也是最容易不稳定的一环。NetScope 最初的判活链路是 `ping` 成功即在线、失败再退回 TCP，结果同一网段连扫三次分别得到 4、6、7 台设备。逐层排查后发现两个独立原因：

1. **资源争抢**：每个主机都 fork 一个 `ping` 子进程，而此时有上千个套接字在并发连接，子进程被饿死，超时判定随机翻转。
2. **协议语义**：ICMP 本来就可以被主机或防火墙丢弃。实测局域网里 `.199` 一直在线且有开放端口，但它不回应任何 ICMP——按 ping 判活，它会永远消失。

修复思路不是“换一个更准的 ping”，而是换一个**判活依据**：TCP 扫描在握手过程中会刷新本机的 ARP 邻居缓存，扫完之后，这个缓存里剩下的单播 MAC 条目，恰好就是刚刚应答过 ARP 请求的设备。也就是说，**邻居缓存本身就是扫描产生的存活证据**。

落地时要满足三条：

- **用扫描自己的副作用当证据**，不要再额外发起请求。这既省掉了子进程，也让判活和扫描结果一致。
- **过滤掉组播/广播 MAC**。`arp -a` 会列出广播地址和 `224.0.0.x` 之类的组播项，它们不是设备。
- **跨网段目标单独处理**。路由可达的地址进不了本机邻居缓存，这类目标仍然用 ICMP，并且用线程池而不是进程池执行。

验证方式是查邻居缓存的语义而不是看总数：扫描后缓存中有 7 台活着的设备全部在列，0 个已下线的单播地址残留。改造后 `/24` 网段 × 6 端口的耗时从 6.19 s 降到 1.14 s，在线设备数稳定为 8 台（含本机）。

这里有一个诚实的取舍：**刚刚掉线的设备可能仍留在缓存里**（ARP 条目有存活时间），会被算成在线。反向的漏报（在线但缓存里没有）更糟，因为真实的在线设备会从结果里消失。宁可短暂多报，也不要让用户以为设备不见了——这个取舍要写进已知限制，而不是假装不存在。

顺带一提，异步改造（用 `asyncio` 的 Proactor 事件循环做非阻塞连接）和存活判定是同一件事的两面：只有当上千个连接不再各占一个线程，扫完一次才可能快到 1 秒级。


## 8. 阶段 6：打包成别人能直接运行的东西

### 8.1 先做三个决策

| 决策 | 选项 | 取舍 |
| --- | --- | --- |
| 单文件 / 目录 | onefile / onedir | 单文件易分发但启动慢；目录启动快但文件多 |
| 控制台 / 无窗口 | console / windowed | 控制台便于看日志和 Ctrl+C；无窗口需要额外的退出机制 |
| 界面形态 | 默认浏览器 / 桌面窗口 | 浏览器零额外依赖，但带地址栏、像网页；桌面窗口像正常软件，但依赖 WebView2 |
| 数据位置 | exe 同级 / 用户目录 | 同级便携；用户目录更符合系统规范 |

NetScope 的选择：单文件、无窗口、桌面窗口、数据放 exe 同级。

这个选择改过两次，值得记录：

- v1 用控制台打包，便于看日志和 Ctrl+C；代价是用户每次启动都会看到一个黑色 cmd 窗口。
- v1.1 改为 `--windowed`（GUI 子系统），黑框消失；代价是必须自己补齐退出、错误提示和单实例处理。
- v1.2 用户反馈“网页界面不像正常软件”，于是用 pywebview + EdgeChromium 把同一套页面装进原生窗口：无地址栏/标签页、自带图标与标题、关闭即退出；浏览器模式保留为回退。
- 结论：**开发期用控制台，交付期用无窗口；产品要“像软件”时，桌面外壳比换技术栈更划算**。不要把调试期的方便当成交付形态。

### 8.2 只读资源与可写数据必须分开

这是打包最常见的坑：

```python
ROOT = Path(__file__).resolve().parent
RESOURCE_ROOT = Path(getattr(sys, "_MEIPASS", ROOT))
APP_ROOT = Path(sys.executable).resolve().parent if getattr(sys, "frozen", False) else ROOT
STATIC = RESOURCE_ROOT / "static"
HISTORY = HistoryManager(APP_ROOT / "data" / "history.json")
```

- **只读资源**（HTML/CSS/JS）从 `_MEIPASS` 读。
- **可写数据**（历史、配置）放 exe 同级目录。
- 源码运行时，两者都回退到项目目录。

不要把“当前工作目录”当作资源根。从桌面快捷方式、其他目录启动时，工作目录并不等于 exe 所在目录。

**还要再分一类：可重建的缓存。** 用户数据（扫描历史）放 exe 同级是对的——复制整个文件夹历史跟着走，删掉文件夹就是彻底卸载，没有残留。但桌面外壳的 WebView2 配置目录是**浏览器缓存**，实测一次启动就长到 12 MB、175 个文件（`GrShaderCache` 4.7 MB、`Default` 4.6 MB、`BrowserMetrics` 1.3 MB），里面没有一条属于用户的东西。把它和历史放在同一个 `data/` 里，用户看到的就变成“一个看不懂的文件夹”，便携目录也显得像残留物。

判断标准不是“哪个目录更专业”，而是**这个文件丢了会不会心疼**：

| 类别 | 例子 | 放哪 | 丢了会怎样 |
| --- | --- | --- | --- |
| 只读资源 | HTML/CSS/JS、图标 | exe 内（`_MEIPASS`） | 重新解压即可 |
| 用户数据 | 扫描历史、配置 | exe 同级 `data/` | 心疼，要跟着文件夹走 |
| 可重建缓存 | WebView2 配置、GPU 缓存 | `%LOCALAPPDATA%\NetScope\` | 无所谓，下次自动重建 |

缓存挪到用户目录还有两个附带好处：多台电脑/多个 Windows 账户各自一份，不会互相串号；卸载 exe 后只剩一份可随时删的缓存。

**门禁**：目录里只留下用户认得的东西。空目录冷启动后，用户看到的应当是**只有一个 exe**（首次扫描后才多出 `data/history.json`），而不是一个装满浏览器垃圾的文件夹。

### 8.3 构建命令

Windows 下 PyInstaller 单文件示例：

```bash
python -m PyInstaller --noconfirm --clean --onefile --windowed \
  --name NetScope \
  --distpath "<项目>/portable" \
  --workpath "<项目>/build" \
  --specpath "<项目>" \
  --add-data "<项目>/static;static" \
  "<项目>/app.py"
```

注意：

- `--add-data` 在 Windows 用分号分隔源和目标。
- 自动生成的 `.spec` 会固化绝对路径，换目录或换机器时不要直接复用；用构建命令重新生成，或改成相对路径。
- 构建前清理旧的 `build` 和 `dist`，避免旧资源混入。
- 覆盖旧 exe 前先确认进程已退出，否则会报 `PermissionError: [WinError 5] 拒绝访问`。
- 验证是否真的无窗口：读 PE 头 `Subsystem`，`2` 是 GUI，`3` 是控制台；不要只凭“双击时没看到”判断。
- 引入 pywebview 后，PyInstaller 会通过自带 hook 收集 `pythonnet` / `clr` 和 WebView2 加载器；不要手工排除 `clr`，否则打包成功但启动即失败。
- 桌面窗口依赖 **Microsoft Edge WebView2 Runtime**（Windows 10/11 通常已预装）。启动时要捕获异常并回退浏览器，而不是白屏或静默退出。
- 体积会变大：加上桌面外壳后，NetScope 一度到 17.4 MB。但这是**依赖被打包进来的结果，不是必须付出的代价**——用排除清单和运行期替身可以把同样的外壳压到 7.2 MB，方法见 8.9。交付说明里要写最终数字，而不是第一次打包的数字。

### 8.4 冷启动验收

必须在一个**空目录**里做，而不是开发目录：

1. 只把 exe 复制到空目录。
2. 双击启动，确认没有任何控制台窗口；桌面窗口带自己的标题和图标，没有地址栏、标签页。
3. 扫描一个已知地址，确认结果、设备类型、MAC、端口。
4. 导出 CSV：桌面形态应弹出原生“另存为”，保存后文件可打开且列正确；取消不应报错。
5. 点击窗口右上角关闭：先取消一次，确认程序仍在且可继续操作；再确认一次，确认进程和 WebView2 子进程都退出、端口释放。
6. 重新启动，确认历史仍在。
7. 运行中再次双击 exe，确认不会启动第二个实例，而是把已有窗口恢复并置于前台。
8. 确认数据写在 exe 同级的 `data` 目录，且该目录里**只有用户数据**——浏览器缓存应已挪到 `%LOCALAPPDATA%`。
9. 删除整个目录，确认无残留（便携软件应可这样卸载）；顺带确认 `%LOCALAPPDATA%` 下那份缓存可以单独删掉。

这九步值得写成脚本，理由是**每次改动都要重跑一遍**：手动点一遍既慢又不可复现。脚本化的三个要点：用 WebView2 远程调试端口读 DOM 和截图（不抢焦点）；用 `EnumWindows` + 进程路径找窗口，不要只按标题找——标题会和遗留的浏览器窗口撞车，导致“关的其实是别的程序”；测试前先确认端口没被上一次遗留的进程占着，否则测的是旧实例。

### 8.5 构建警告与 SmartScreen

- PyInstaller 的缺失模块警告里，大量是 POSIX 或可选模块；判断标准是“冻结后的程序是否真的用到”，不要盲目补模块。
- 未签名 exe 可能触发 SmartScreen；交付说明里写清楚“更多信息 → 仍要运行”，不要假装不存在。
- 控制台程序要说明如何退出（Ctrl+C 或关闭窗口）；无窗口程序必须有明确的退出路径：桌面窗口用右上角关闭 + 原生确认，纯浏览器形态才需要页面内退出入口。

### 8.6 无窗口打包要补齐的三件事

去掉控制台不是加一个 `--windowed` 就结束，它同时去掉了三条默认能力：

1. **退出**。没有 Ctrl+C。桌面窗口用 pywebview 的 `closing` 事件弹原生 `MessageBoxW`（是/否、默认否、置顶）：取消返回 `False` 阻止关闭，确认才销毁窗口并停服务。受令牌保护的 `POST /api/shutdown` 先设置“正在退出”标志，再走同一条关闭路径，因此程序化退出不再二次询问。桌面形态**不要**再放侧栏退出按钮——入口重复会让用户困惑；只有浏览器回退形态才显示页面内退出按钮。
2. **错误可见**。启动失败时没有 stderr。冻结环境下用 `MessageBoxW` 弹原生对话框，覆盖端口被占用、端口越界、桌面窗口打不开；源码运行仍回退到 `print`。
3. **单实例**。再次双击 exe 时，先请求 `/api/health` 判断是不是本程序。桌面形态用窗口标题 `FindWindowW` 找到已有窗口，最小化则 `ShowWindow(SW_RESTORE)`，再用 `AllowSetForegroundWindow` + `BringWindowToTop` / `SwitchToThisWindow` + `SetForegroundWindow` 把它带到前台；浏览器形态直接打开页面。第二个进程应在 1～2 秒内退出，而不是启动第二个服务。

还要分清两种形态的退出语义：**浏览器形态下，关闭页面不等于退出进程**，必须显式调用关闭接口或在进程管理器中结束；**桌面形态下，关闭窗口就是退出程序**。交付说明必须写清楚当前是哪一种。

**门禁**：空目录冷启动成功，核心流程可用，重启后数据仍在，退出后无残留进程。

### 8.7 桌面外壳：把网页装进原生窗口

用户说“功能很全，但不像一个正常软件”时，问题通常不在功能，而在运行形态。两条路：

- **换技术栈**（Electron/Tauri/重写原生）：收益大、成本也大，已有 Web 界面几乎要重做集成。
- **加桌面外壳**（pywebview + EdgeChromium）：复用全部前端，只换容器；代价是多一个依赖和更大的体积。

NetScope 选了后者，值得记录的坑：

- **窗口尺寸的单位是逻辑像素**。在 150% DPI 的屏幕上，`create_window(width=1440)` 实际得到 2160 物理像素。按 `screen.width * 0.92` 计算并夹住最小值，再按逻辑坐标居中，才能既不过界也不显得太小。
- **启动白屏不一定是页面坏了**。WebView2 使用 DirectComposition，父窗口的 `PrintWindow` 可能只拿到白色；截子窗口 `Chrome_WidgetWin_0` 才能看到真实内容。窗口从最小化恢复后也可能不重绘，在 `shown` / `restored` 事件里 `RedrawWindow` 一下即可。
- **WebView2 不会像浏览器那样下载文件**。`window.location.href` 指向 CSV 接口在浏览器里能下载，在桌面窗口里可能毫无反应。正确做法是通过 pywebview 的 `js_api` 暴露一个 `save_csv` 方法，内部用 `comdlg32.GetSaveFileNameW` 弹原生“另存为”，写文件后把路径回传给页面提示；浏览器形态仍走原来的 URL 下载。
- **不要用前台窗口猜测来验收**。测试时窗口可能被最小化或挡在 IDE 后面，鼠标自动化会点错目标。用 WebView2 的远程调试端口执行 JS（`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333`），既不抢焦点，也能读到 DOM 和截图；需要原生对话框时再用 `FindWindow` + `PostMessage` 驱动。调试日志用环境变量开关（如 `NETSCOPE_DEBUG_WEBVIEW=1`），不要常驻打开。
- **外壳的退出要和窗口生命周期绑定**。窗口关闭事件返回 `False` 可以取消关闭，正好用来做确认；确认后要停扫描、停 HTTP 服务、销毁窗口，并检查 `msedgewebview2` 子进程是否随 profile 一起退出。
- **体积换体验要提前说**。纯标准库版本约 9 MB，加外壳后一度到 17.4 MB（依赖全量打包的代价）；做完 8.9 的体积治理后，同一套外壳是 7.2 MB。换了双击即开、独立图标、无地址栏、关闭即退出，同时把体积讲清楚，用户才不会觉得“怎么突然这么大”。

### 8.8 设备类型识别：离线 OUI + 多特征组合

“能识别设备类型吗”很容易被理解成“查一下 MAC 厂商”就结束，但只靠 OUI 会得到一堆“小米设备”“Samsung 设备”，对使用者帮助有限。NetScope 的做法是三层特征叠加，并保持保守：

1. **离线 OUI 厂商表**：从 IEEE MA-L 公共注册表生成 `oui.py`，只保留家庭/小型办公常见厂商，按品牌分组。当前快照为 62 个厂商组、11,652 个前缀，随程序打包，不联网查询，避免泄露内网信息。
2. **主机名线索**：如 `iPhone-Alex`、`LivingRoom-TV`、`MacBook-Pro`、`DESKTOP-XXXX`；先匹配强特征，再用分隔符边界匹配 `tv`、`pc`、`nas`，避免 `steven` 里的 `tv` 之类误判。
3. **端口签名**：62078（Apple 锁定服务）→ 手机/平板；515/631/9100 → 打印机；554/8554/37777 → 摄像头；32400 → 媒体服务器；5555 → Android 手机；135/139/445/3389 → Windows；22 → Linux/SSH；1883/8883 → MQTT 智能设备。

判定顺序是“主机名强信号 → 设备专属端口 → 厂商类别 → 通用端口 → 未知设备”。厂商类别只能给到可信的上位概念时，不要硬猜具体型号：Samsung 只有出现电视端口或电视主机名才显示“Samsung 电视”，否则就是“Samsung 设备”。中文品牌和英文品牌拼接要处理空格（`小米手机`、`OPPO 手机`），否则界面会显得像机器翻译。

两个容易踩的坑：

- **随机化 MAC**：手机默认开启“私有 Wi-Fi 地址”时，MAC 的本地管理位（第一个字节的 `0x02`）会被置位，OUI 查不到厂商。这类设备只能靠主机名/端口识别，仍可能显示“未知设备”，这是数据本身的上限，不是程序漏了。
- **OUI 重复归属**：同一前缀可能同时出现在 Lenovo 和 Motorola 的组织名里。生成表时要显式去重（当前校验为 0 个重复前缀），否则后写入的厂商会覆盖前一个，测试样例也会随机失败。

验收不能只看单元测试。NetScope 这轮用真实局域网扫描验证：网关 `08:40:F3` 最初落到“Web / 应用服务”，补入 Tenda 后变为“Tenda 路由器”；`50:BD:5F` 显示“TP-Link 路由器”；同时检查结果表、历史详情、CSV 三处都使用同一字段。源码和冻结 exe 各跑一遍，才算完成。

### 8.9 体积治理：把 17.4 MB 的 exe 压回 7.2 MB

“加外壳之后体积翻倍”常被当成必然。NetScope 的桌面版一度是 17,447,016 字节，真正的原因不是 WebView2，而是**打包工具把所有能被静态分析到的依赖都塞了进去**。用一轮排除清单把它压到 7,220,074 字节（-58.6%），功能不减。

**方法：先画依赖图，再判断运行时必要性。**

1. 从 PyInstaller 的 `Analysis-00.toc` / xref 拿到真实导入图，看清楚每个候选是被谁拉进来的。
2. 对每个候选问两个问题：**它是模块级导入还是函数内延迟导入？运行期真的会走到吗？** 只按“属于标准库/第三方”排除是错的——`asyncio`、`email`、`http.client` 都在用，而 `unittest`、`pdb`、`sqlite3` 只是被顺带扫到。
3. 只有确定运行期不用的才排除；对“模块级导入但运行期可能走到”的，用**运行期替身**顶上，而不是删掉。

**收益最大的几项**

| 排除对象 | 省下 | 说明 |
| --- | --- | --- |
| `_hashlib` | ~1.77 MB | `hashlib` 会连带拉入 `libcrypto-3.dll`；标准库自带 `_sha2`/`_md5`/`_sha3`/`_blake2`，功能不缺 |
| `ssl` / `_ssl` | ~0.3 MB | 服务只在 `127.0.0.1` 上走明文 HTTP |
| `zipfile` / `tarfile` | ~0.1 MB | 见下面的坑 1 |
| `bottle` | ~0.1 MB | 只有 pywebview 的 WSGI 服务器需要，用替身顶替 |
| `unittest` / `pdb` / `sqlite3` / `multiprocessing` / `tkinter` | ~0.2 MB | 窗口程序永远走不到 |
| `xml` / `urllib.request` / `decimal` / `statistics` | ~0.3 MB | 只服务于永远不会执行的错误分支 |
| `webview.platforms.*`（非 Windows） | ~0.2 MB | Qt/GTK/Cocoa/CEF 后端 |
| WebView2 的 arm64/x86 加载器 | ~0.27 MB | 见下面的坑 4 |

**四个坑，每一个都会让“打包成功”变成“启动失败”**

1. **`zipfile` 不能排除。** PyInstaller 自己的运行时钩子 `pyi_rth_inspect` 要读 `base_library.zip`，排除后冻结版启动即报 `No module named 'zipfile'`。**打包工具的运行时钩子是你排除清单的下界**，先读一遍它们。
2. **`cffi` 和 `_cffi_backend` 不能排除。** `clr_loader/ffi/__init__.py` 在模块级 `import cffi`，而 `cffi.FFI()` 又直接 `import _cffi_backend`；两者任缺其一，桌面外壳就起不来，报 “Failed to create a .NET runtime (coreclr)”，程序会**静默回退到浏览器**，看起来只是“没有窗口”。判断依据应该是“冻结版有没有真的起窗口”，不是“依赖在不在”。
3. **排除 `distutils` 会让构建直接失败。** Python 3.12 起 `distutils` 由 setuptools 提供，PyInstaller 的 pre-safe-import 钩子会把 `setuptools._distutils` 别名成顶层 `distutils`；一旦 `distutils` 已在排除列表里，构建报 `ValueError: Target module "distutils" already imported as "ExcludedModule"`。解法是自己写一个同名钩子（用户钩子优先级高于内置钩子）跳过这次别名。
4. **WebView2 的运行库目录必须“存在”，但里面的 DLL 可以没有。** pywebview 启动时执行 `interop_dll_path('win-arm64')`，而它只判断**目录**是否存在，不看目录里的文件。所以丢掉 arm64/x86 的加载器后，桌面外壳报 `Cannot find win-arm64` 直接罢工。解法：保留目录、放一个说明文件（不能叫 `WebView2Loader.dll`，否则 .NET 会挑错架构的加载器）。

**替代品要带明确的失败信息。** `runtime_hook.py` 只在真模块缺失时安装替身：`ssl`、pywebview 需要的 `bottle.ServerAdapter`、`typing_extensions`（3.13 起这些名字 `typing` 都有）、`xml.etree.ElementTree`。每个替身都打 `_netscope_stub` 标记，并且让 `parse()` 抛出“便携版未包含 XML 解析器，无法读取 .NET 错误详情”这类**能看懂的中文提示**，而不是在扫描跑到一半时抛一个 `AttributeError`。

**先模拟，再打包。** 重建一次要 25 秒，改一个排除项再验证要 25 秒，太慢。写一个“冻结模拟”脚本：用一个 `sys.meta_path` 钩子拒绝对应模块，再装上运行期替身，然后完整跑一遍应用（导入、起 HTTP 服务、健康检查、真实扫描）。它能在 2 秒内验证排除清单是否自洽，**但它证明不了冻结包真的能用**——真实冻结版的验收仍然必须做，尤其是桌面外壳。

**验收要自动化。** 用 WebView2 的远程调试端口读 DOM 和截图，用 `EnumWindows` + `QueryFullProcessImageNameW` 按**进程**找窗口（只按标题找会撞上遗留的浏览器窗口），用 `FindWindow("#32770")` 找原生确认框。这套脚本让“桌面窗口能起、扫描能跑、退出要确认、端口要释放”变成一条命令。

**门禁**：排除清单有据可查（每个排除项都写清为什么运行期用不到），冻结版冷启动 + 桌面外壳 + 扫描 + 导出 + 退出确认全部通过，体积数字写进交付说明。

### 诚实说明边界

NetScope 的已知限制包括：

- 未签名，Windows 可能提示。
- 设备类型是启发式推断，不是权威识别；依据为离线 IEEE OUI 快照（62 个厂商组、11,652 个前缀）、主机名和端口特征。
- 开启“私有 Wi-Fi 地址”的手机、未知厂商或没有开放端口的设备，可能显示“未知设备”。
- 远端 MAC 依赖 ARP/邻居缓存，跨网段或缓存未命中时可能为空。
- **存活判定以扫描刷新的邻居缓存为依据**：刚掉线的设备可能短时间内仍显示在线（宁可短暂多报，也不让在线设备消失）；跨网段目标仍用 ICMP，被防火墙丢弃时会漏报。
- 不适合公网扫描或漏洞探测。
- 单文件 exe 首次启动会比源码慢。
- 卸载时删掉整个文件夹即可，但 `%LOCALAPPDATA%\NetScope` 下会留下约 13 MB 的 WebView2 缓存（可随时手动删除，不影响功能）。

写清楚这些，不会降低交付质量，反而会减少误用和支持成本。

## 10. 换模型：交接的是状态，不是聊天记录

### 10.1 四个文件

在项目根目录维护四个短文件，模板在 [project-template](project-template)。新项目开始时，直接把这四个文件复制到项目根目录并填写；`TASK_CARD.md` 和 `HANDOFF_PROMPT.md` 按需使用。

| 文件 | 作用 | 更新时机 |
| --- | --- | --- |
| `PROJECT.md` | 目标、非目标、验收、约束 | 需求变更时 |
| `ARCHITECTURE.md` | 边界、契约、数据、失败模式、决策 | 接口或结构变化时 |
| `PROGRESS.md` | 已完成、进行中、下一步、阻塞 | 每次会话结束 |
| `TEST_LOG.md` | 命令、结果、环境、未验证项 | 每次测试后 |

原则：

- **聊天记录不是事实来源，文件才是。**
- `PROGRESS.md` 控制在 60 行以内，只留当前有效信息。
- 决策要写“为什么”，否则新模型会反复推翻。
- “不要重复做的事”单独列出来，能省大量时间。

### 10.2 新模型启动提示词

```text
你将接手这个项目。先完整阅读：
- PROJECT.md
- ARCHITECTURE.md
- PROGRESS.md
- TEST_LOG.md

不要修改任何代码。用 10 行以内复述：
1. 项目目标与非目标；
2. 架构边界与关键契约；
3. 已完成内容和验证方式；
4. 当前阻塞；
5. 下一步任务。

然后指出文档中互相矛盾、缺失或过时的信息。
确认后，只执行 PROGRESS.md 中“下一步”的第一项，不要扩大范围。
```

### 10.3 换模型后的 30 分钟校准

不要一上来就让新模型做大功能。先用一个小任务校准：

1. 给它项目简报、架构和一个明确的小 bug。
2. 要求先给根因和验证方法，再改代码。
3. 看它是否真的运行测试、是否贴出证据。
4. 看 diff 是否克制、是否遵守“不允许改动”。
5. 通过后再逐步放大任务。

校准的不是“模型聪不聪明”，而是“它是否遵守流程”。

### 10.4 交叉验收

可以让第二个模型做评审，但只给它：

- `PROJECT.md`
- 变更 diff
- `TEST_LOG.md`
- 验收清单

不要给它原作者的自我解释，避免被带偏。评审只回答：验收是否成立、是否有回归、证据是否充分。

### 10.5 新项目启动顺序（可直接照做）

1. 复制 `docs/project-template/` 下的四个状态文件到新项目根目录，填写 `PROJECT.md`。
2. 发开工提示词，确认目标、非目标和方案取舍。
3. 让模型输出 `ARCHITECTURE.md`，确认模块边界与契约后再写代码。
4. 发 MVP 提示词，只做纵向切片；真实验收后更新 `PROGRESS.md` 和 `TEST_LOG.md`。
5. 每个需求或 bug 用一张 `TASK_CARD.md`，一次只推进一项。
6. 阶段末做加固与打包，按发布清单验收；换模型时发 `HANDOFF_PROMPT.md`，先校准再放大任务。

## 13. NetScope 复盘：流程如何落到实际

### 开发时间线

| 阶段 | 做了什么 | 关键产出 |
| --- | --- | --- |
| 立项 | 明确本地扫描、中文界面、最终免安装 | 功能边界与验收标准 |
| 方案 | 标准库、本地 HTTP、令牌鉴权、模块拆分 | `scanner.py` / `app.py` / `static/` |
| MVP | 解析、探测、任务、页面 | 能完成一次真实扫描 |
| 功能迭代 | 历史记录、设备类型、MAC、整行点击 | 完整的结果与历史体验 |
| 问题修复 | 历史打不开、MAC 不符、网段语义、打包路径 | 根因明确的修复与回归 |
| 加固 | 输入限制、鉴权、CSP、原子写入、CSV 防注入 | 可解释的失败行为 |
| 打包 | PyInstaller 单文件、资源/数据路径分离 | 9.0 MB 便携 exe（浏览器形态） |
| 打包修正 | 交付版改 `--windowed`，补原生错误对话框、单实例 | 启动无 cmd 窗口的 exe |
| 桌面化 | pywebview + WebView2 外壳；关闭确认；原生 CSV 另存为 | 17.4 MB 独立桌面窗口 exe，浏览器回退保留 |
| 设备识别 | 离线 OUI 快照 + 主机名/端口特征；补 Tenda、H3C、锐捷、水星、烽火、ZTE 厂商 | 品牌级设备类型，未知设备保持诚实 |
| 性能与体积 | 邻居缓存判活、asyncio 扫描、长连接刷新；依赖排除清单与运行期替身 | 扫描 6.19 s → 1.2 s；exe 17.4 MB → 7.2 MB |
| 交付 | 空目录冷启动、重启持久化、清理测试数据 | 可独立运行的成品 |

### 关键决策

- **标准库优先，外壳例外**：扫描、HTTP、存储、CSV 仍用标准库，降低核心逻辑的依赖风险；只为“像正常软件”这一目标引入 pywebview + pythonnet，并保留浏览器回退。
- **本地 HTTP + 随机令牌**：不暴露服务，同时保留 Web 界面的开发效率；桌面外壳只是这个本地服务的一个视图。
- **开发用控制台，交付用无窗口**：控制台便于看日志和 Ctrl+C；交付去掉黑框，但必须补原生错误对话框、退出确认和单实例处理。黑框不是 Python 的 bug，是打包时的子系统选择。
- **桌面形态关闭窗口即退出，浏览器形态不是**：桌面窗口把关闭事件绑到停服务；浏览器只是客户端，必须显式退出。两种形态的说明不能混用。
- **入口只留一个**：桌面形态只用右上角关闭，不再提供侧栏退出；重复入口会让用户犹豫“到底点哪个”。浏览器回退才显示页面内退出按钮。
- **JS 能做的交给页面，做不了的走 js_api**：CSV 内容由页面请求后端生成，但“选保存位置”必须落在原生层；WebView2 不处理下载，不能照搬浏览器写法。
- **JSON 历史而非数据库**：零依赖、易迁移；代价是数据量大时性能有限。
- **整行可点击**：数据和 API 正确不代表可用，交互必须单独验收。
- **按活动 IP 匹配网卡 MAC**：环境相关问题必须用环境证据定位，不能靠猜。
- **设备识别宁可保守**：先给“Tenda 路由器”这类有证据的品牌级结论；没有主机名和端口证据时，不把厂商表里的“Samsung 设备”硬猜成电视或手机。随机化 MAC 显示“未知设备”比编一个型号更可信。
- **OUI 表离线内置**：设备识别不访问公网，内网 MAC 不会离开本机；代价是表需要随 IEEE 快照更新，新厂商可能暂时识别不到。
- **只读资源与可写数据分离**：源码运行和冻结运行的行为要一致。
- **依赖要主动瘦身**：打包体积是选出来的，不是默认的。排除清单必须以运行时证据为准，删错了不会报错、只会静默回退（桌面外壳没了 cffi 就变浏览器模式），所以每次瘦身都要跑一次冻结版验收。

### 最终数字

## 14. 一页版执行清单

如果只记住一页，就按这个顺序做：

1. **写简报**：目标、非目标、运行形态、可观察验收。
2. **定契约**：模块边界、API、数据格式、失败模式、测试策略。
3. **做闭环**：解析 → 探测 → 任务 → HTTP → 最小页面 → 真实扫描。
4. **验界面**：空/加载/运行/成功/错误/禁用，真实浏览器 + 键盘。
5. **迭代**：复现 → 根因 → 验收 → 最小改动 → 双层验证 → 回归。
6. **加固**：输入、并发、鉴权、持久化、输出、隐私逐项对抗测试。
7. **打包**：资源/数据路径分离，空目录冷启动，重启持久化。
8. **交接**：更新四个状态文件，清理测试数据，交付成品 + 说明 + 限制。

每次只推进一步，每步留下证据。模型可以换，证据和状态不能丢。
